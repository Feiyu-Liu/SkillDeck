## M4-1: pending Lineages and 404

**The case:** contract v0.1 deletes a Lineage that is never advanced after 24
hours, and frees its `clientKey` (decided today, Q1 from T20). Take a laptop
that creates a Lineage, loses the network before its upload, and sleeps for a
day.

**What the Reconciler does on wake** (`reconciler.dart`):
- The link already stores the `lineageId`, so `_reconcile` reads the Lineage.
  The read answers 404, and the outcome is Needs Attention, "Missing from the
  Cloud Library after a reset" (lines 189–192). The Skill was never in the
  Cloud Library, so the reason is wrong, and its "Upload it as a new Cloud
  Lineage" action uses a new `clientKey`.
- If the Lineage disappears between the read and the upload, `uploadPack` or
  `advanceHead` answers 404 `notFound`, which both list as a documented error.
  `_failure` throws `StateError('cloud_protocol')` for it (line 429). That
  aborts the check for every other Skill too.

**My part:** when answering Q1, I said I would add the 404 rule to T23. I did
not, so the card never asked for it.

**Fix:** a link that still holds its `clientKey` has never been advanced from
this Device. On 404 from read, upload, or Head Advance for such a link, clear
the `lineageId` and create again with the same key, then continue. For a link
without a `clientKey`, a 404 from upload or Head Advance means the Lineage was
removed meanwhile: read it again, and treat a 404 from that read as today.

## M4-2: Needs Attention holds the feed cursor

**What happens:** `_settled` counts only Synced, Device Only, and Removed as
settled (lines 433–436). In `feedCheck`, an entry whose outcome is Needs
Attention leaves the page unsettled, so the cursor stays and the check returns
`FeedCheckResult.failure` (lines 146–155). `checkLocalChanges` does the same.

**Why it matters:** an Attention Reason waits for the person, often for days,
for example a Sync Merge conflict or a Draft. Until then:
- every check counts as a failure, so T04's scheduler backs off to 30 minutes
  for all Skills, not only the blocked one;
- every check reads the same page again, then downloads and applies the blocked
  Skill's pack again, up to 16 MiB each time;
- a later page is never read while the blocked entry sits on an earlier page.

**Fix:** only a retryable outcome (Waiting to Upload) should hold a cursor or
fail the check. Needs Attention and account conditions are settled for the
cursor: the check succeeds and moves on. Keep the blocked Skill's outcome, and
reconcile it again when one of these happens:
- the person uses a resolving action;
- a local committed change touches the Skill;
- a later feed entry changes its Lineage.

**Check first:** whether publishing or discarding a Draft, and resolving a Sync
Merge conflict, appear in the Workspace committed-change feed. If one does
not, that Skill would wait for an unrelated change. In that case, reconcile
the Skills that hold an Attention Reason on each check, without holding the
cursor, and without downloading again when the Lineage `version` and the local
Effective are unchanged since the last attempt.

## M4-3 to M4-5: Nits

- **M4-3:** in `feedCheck`, an entry for a Lineage with no link here that
  answers 404 records `missingAfterReset` under the Lineage ID (lines
  140–145). Nothing is on this Device, so skip it.
- **M4-4:** the service answers 410 `cursorExpired` on a library page when the
  tombstone sweep raises the floor during a listing. `bootstrap` passes that to
  `_failure`, which throws. Restart the listing from the first page instead,
  once per bootstrap.
- **M4-5:** `_lineage` in `cloud_api.dart` rejects `/`, `.` and `..` only. An ID
  containing `?`, `#` or `%` would change the request URL. The service mints
  UUIDs, so accept only `[A-Za-z0-9_-]` up to 64 characters, matching the
  contract's "opaque, at most 64 characters".

## M4-6: Synced Origin round trip (for the M7 adapter)

`_reconcile` starts a Generation change whenever the local Portable Source
differs from the Lineage's `source` in the same Generation (lines 246 and
293). On a Device that installed a Device-Bound Lineage, the local Source is a
Synced Origin Source. The fake returns the same Portable Source, so the tests
pass. If the real adapter maps a Synced Origin Source back to anything
different, even one changed label, then every check on that Device starts a
new Generation, and every other Device applies it.

**For the M7 adapter card:**
- a round-trip test: install a Device-Bound Lineage through the real Workspace,
  read it back through the adapter, and compare with the Lineage's `source`;
- optionally, start a Generation change only when the committed-change feed
  says the Source was replaced, not on a comparison alone.

## M4-7: no test of the Dart client against the real Worker

Both sides follow the contract closely, and I checked the strict points by
reading both:
- `Content-Type` and `Content-Length` on a pack download;
- the `SkillDeck-Pack-Roots` header;
- the 201 on create;
- the error bodies;
- the limits of 500 for the library and 1,000 for the feed.

But staging was driven by the service's TypeScript qualification script; only
a 401 probe used the Dart User-Agent. A short run of `CloudApi` against
`wrangler dev` would prove the client and the Worker agree. The packs would
come from the prototype Device CLI or the native export, since the Worker
rejects the fake pack encoding. This is the maintainer's choice; I suggest
doing it with the M7 adapter, when real packs exist on the client.

## Service side: notes, no findings

- **Feed and cursors:** the cursor carries an account tag and a sequence.
  - A malformed cursor gets 400.
  - A cursor with another account's tag, a sequence beyond the issued one, or
    a sequence below the tombstone floor gets 410.
  - This matches the two decisions.
- **Ending wins:** the Head Advance compare-and-swap requires `state='live'`,
  and a lost race is answered from a fresh read. An advance after an end gets
  410 `lineageEnded`.
- **`clientKey`:** create removes the account's expired pending Lineages in the
  same batch, so a retry after 24 hours creates a new Lineage, as decided.
- **Commit graph:** Head Advance checks descent with a recursive query over the
  stored parent edges of the Generation. Edges come only from verified packs.
  An edge is a fact of the commit's own hash, so leftover edges from an
  unfinished upload cannot make a false descent.
- **Retention:** the staging record observed the 15-minute sweep clear the aged
  packs, edges, and ended Generations, with tombstones kept.
- **T18:** the approval page claims a code only once per account, and shows
  "Too many attempts" on a 429. The lockfile now resolves only from the public
  npm registry.
