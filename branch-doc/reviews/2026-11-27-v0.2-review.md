# v0.2 元数据契约评审

日期：2026-11-27。评审基线：`1e993ab`。
对象：`branch-doc/cloud-api-contract-v0.2.md`，对照 v0、v0.1、R5、
Cloud CONTEXT 和当前 Workspace/App 接口。

**结论：暂不定稿。总体结构可以保留，下面四个正确性缺口需要明确，
笔记冲突方案需要收敛。** 本文是评审意见，不代表维护者已批准新的语义。
没有修改原契约或生产代码。

## V02-1：本地读取与应用之间的写入保护必须定案

- 位置：v0.2 第 349–356、386 行。
- 级别：阻塞定稿，涉及本地数据覆盖。

反例：同步读到 Note=A，准备应用远端 Favorite=true，同时保留 Note=A。
此时 CLI 或 UI 把 Note 改成 B。内容的 Effective Revision 没有变化，
旧请求的 `RemoteSkillMetadata(..., note: A)` 仍能通过检查，把 B 覆盖。
事后重读无法恢复已经被覆盖的 B。

草案已承认这个缺口，但把“是否存在绕过队列的写入者”留给 T34。
当前代码已经存在这样的入口：

- `skilldeck-app/lib/features/library/skill_library_providers.dart:40`
  直接通过 App repository 保存笔记；
- `skilldeck-app/lib/features/command_host/data/write_command_handlers.dart:407`
  通过同一 repository 写收藏、笔记和标签，但不进入 Cloud runtime 队列；
- `packages/skills_workspace/lib/src/composition/metadata_command_handlers.dart:288`
  只比较请求携带的 Effective，然后用提交的全部元数据调用 `setMetadata`。
  引擎自身的事务串行化不能识别调用者在进入操作之前读到的旧值。

**建议：** 在契约中要求“本地读取时的状态仍然匹配”才能应用远端结果。
优先评估复用本地 RepositoryRevision 或预期本地值的事务内比较；失败就
重新读取并对账。词表更新也应覆盖相同的读取/应用窗口。不要把服务端
Field Version 引入 Workspace，也不要跨网络请求长期锁住用户编辑。

验收：在读后、应用前插入一次 UI/CLI Note、Favorite 或标签修改；旧应用
必须拒绝或重算，不能覆盖新的本地值。

## V02-2：首次启用和状态丢失时，没有元数据基线规则

- 位置：v0.2 第 70–77、300–315、328–339 行。
- 级别：阻塞定稿，涉及首次同步的数据方向。

服务端默认值是 Favorite=false、Note=null、空标签集合。客户端用“本地值
与上次已对账值的差异”判断待上传，但 M4 升级到 M6 时没有元数据的已对账值。
本地同步状态文件损坏或重建也会失去基线。

因此，直接应用 bootstrap 可能清空原设备已有的笔记；把所有本地值当成
待上传，又可能让新安装 Skill 的默认值覆盖已有云端数据。匹配到本地已有
Skill 的 bootstrap 也不能等同于刚创建的空 Skill。

**建议：** 明确区分新安装、关联已有本地 Skill、v0.1 升级和丢失本地同步
状态这四种入口。可采用以下方向作为待确认规则：

- 新安装的空 Skill 以云端值初始化；
- 服务端尚未编辑的字段（版本 0）允许已有本地值以 CAS 初始化；
- 没有基线且双方存在不同的非空 Note 时，保留两份，不能猜测哪份更新；
- 没有基线时，Favorite 与 Tag Assignments 的初始化优先级必须写明。

验收：上述四种入口分别覆盖本地非空/远端空、远端非空/本地默认、双方
不同的 Note，以及初始化过程重启；所有有效笔记均可恢复或由用户明确取舍。

## V02-3：标签仅按名称重试创建，会重建已改名或删除的标签

- 位置：v0.2 第 225–239 行。
- 级别：阻塞定稿，涉及创建、改名和删除的并发语义。

反例：设备 A 创建标签“研究”，服务端创建 t1，但成功响应丢失。设备 B
看到 t1 并把它改名为“阅读”。A 尚未保存本地标签到 t1 的映射，重试创建
“研究”；按当前规则，该名称已空闲，于是产生 t2。用户看到“阅读”和重新
出现的“研究”。若 B 删除 t1，同样可能被创建重试复活。

重复名称返回已有标签，只能处理名称仍未变化的情况。

**建议：** 为创建提供稳定的关联身份，使同一个本地创建能找回已改名、
合并或删除后的对象。可复用已有标签别名/合并映射的概念；明确其保留和
过期规则，不需要引入客户端操作回放队列。若选择允许重建，应把这种用户
可见结果写成明确的产品取舍，不能当作丢失响应已经被正确处理。

验收：创建成功但响应丢失，另一设备分别执行改名、合并或删除，然后原
设备重试；不得无说明地产生第二个逻辑标签。

## V02-4：合法分页可能超过现有客户端响应上限

- 位置：v0.2 第 130–134、283–303 行。
- 级别：定稿前必须补齐的传输约束。

一页允许 500 个 Skill，每个 Note 可有当前文本和两个冲突文本，单个文本
允许 4 KiB。按这些上限编码 500 条元数据，仅 metadata 部分就是
**6,303,014 字节**，尚未计入 Lineage、词表和标签分配。

当前 `packages/skills_cloud/lib/src/api/cloud_api.dart:25` 的 JSON 上限为
**4,194,304 字节**，第 162 行会拒绝更大的响应。因此，服务端完全遵守草案
也可能令客户端 bootstrap 失败。JSON 转义还可能进一步放大正文。

**建议：** 定义按编码后字节数限制分页，`limit` 只是条数上限；单页可以
提前结束，并返回可继续的游标。与客户端的有界响应读取共同验证，不要靠
无限扩大内存上限解决。

验收：最大 Note、三份冲突文本、最大标签分配、需要 JSON 转义的文本，
都能通过有界分页完整遍历，且不遗漏或无限重试。

## V02-5：笔记历史方案过重，还会对已经一致的值制造冲突

- 位置：v0.2 第 164–216、381–382 行。
- 级别：需要维护者定案的简化建议；现方案本身已标为未决提案。

现提案为了重建精确的历史竞争文本，保留 Lineage 存续期间每个 base 的
已接受文本，以及已处理候选的识别数据。这超出了“发现笔记不同，保留两份
让用户选择”的基本体验，增加了长期存储、清理和重试状态。

还有一个具体结果：A 从版本 0 写成 X，后来又写成 Z；B 离线从版本 0
也写成 Z。双方当前文本已经都是 Z，但第 171–175 行仍要求把 B 的 Z
与历史 X 比较，进而可能产生 X/Z 冲突。这会重新提出用户已主动改掉的旧文。

**建议：** 优先以“当前已接受文本”和“传入文本”判断是否存在需要处理的
差异；相同则收敛，不提示冲突；不同则保留两份。第三份未同步的本地编辑
不能被后续远端应用覆盖。明确这种语义与 R5“同一 Field Version”表述的关系，
经维护者确认后再改正文。

简化不能顺带承诺无历史记录也能完全消除重复提示。冲突创建/解决的响应
丢失、第三设备晚到修改，需要给出状态演算和验收案例；可以讨论是否接受
少量重复确认，以避免无限历史账本，但不能默许丢失文本。

## 可以保留的部分

- 元数据与内容版本独立；每字段 CAS，普通收藏和标签按服务端接受顺序收敛。
- 复用 Account Change Feed 和现有游标；旧客户端忽略新 kind 的约定与代码匹配。
- bootstrap 使用起始 feed cursor 作为回放下界，无需持久化多页快照。
- 标签名使用现有 Workspace 的 trim、NFC、NFKC 和 uppercase 规则；本次
  代码核对未发现归一化规则不一致。服务端仍需做跨运行时等价测试。
- 服务端 tag ID 与 Field Version 留在 Cloud；Workspace 只接收本地身份和值。

另一个应明确的产品边界：本地标签是整个 Workspace 共用的。远端词表删除
会移除所有使用该标签的本地分配，包括 Device Only Skill。草案应说明这是否
是账户词表的预期行为，以及切换 Cloud 账户时如何处理本地已有词表。
