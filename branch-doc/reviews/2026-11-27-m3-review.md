## T17-1: approval page and the plugin's per-IP limit

**What happens:** each signed-in load of `/device` calls the plugin's
`GET /api/auth/device` to claim the code. The plugin limits that path to
5 requests per code lifetime (10 minutes) per client IP. From the 5th load
on, the plugin answers 429, and the page shows "This sign-in request is
invalid or expired. Start again in SkillDeck."

**Reproduced on dev:** across two sign-ins from one address, loads 1–4 showed
the review page and loads 5–7 returned 429 with that text. Approving still
worked, because approval does not call the claim endpoint.

**Why it matters:**
- The limit is per IP address, not per person or code. People behind one
  office or carrier NAT share it.
- One person who reloads a few times sees a false "expired" message.
- The message sends them back to SkillDeck to start over, which uses up
  another load.

**Suggested fix, the service's choice of which:**
- claim the code only once: skip the claim when the row already belongs to the
  signed-in account;
- or override the plugin's limit for that path through Better Auth's custom
  rate-limit rules;
- in either case, show a "too many attempts, wait a minute" message for 429
  instead of "invalid or expired".

## T17-2: 429 is outside the contract

**What happens:** Better Auth's global limit is 100 requests per 60 s per IP
and path. When it trips, the service answers HTTP 429 with
`{"error": "rate_limited"}`. The device-code limit and the email-OTP quota
answer the same way.

**Effect on T16:**
- `start` reports a protocol failure;
- `complete` ends the sign-in with a protocol failure;
- `currentSession` reports unavailable with a protocol failure, which keeps
  the token.

At a 5-second interval, one Device polls 12 times a minute, so the polling
limit trips only behind a shared NAT with many Devices signing in at once.
Even then, it should not end a sign-in.

**Suggested change:**
- The contract adds HTTP 429 to the conventions as "try again later". It does
  not use the RFC 8628 error table.
- **T16, `complete`:** a 429 keeps polling at the current interval, as a 5xx
  does.
- **T16, `start` and `currentSession`:** a 429 reports `server`, not
  `protocol`.
- This is a few lines and one test per call.

## T17-3: npm mirror in the lockfile

All 355 `resolved` URLs point at a mainland-China mirror of the npm registry.
From this session that host did not answer, and `npm ci` made no progress in
ten minutes. Installing with `--registry=https://registry.npmjs.org/
--replace-registry-host=always` worked, and npm still verified every
package's integrity hash.

Mainland China is out of scope for the product. The lockfile is also build
input for CI and for deploys from Cloudflare's network. Suggest regenerating
it against `registry.npmjs.org`.

## T17-5: the earlier design is still in the repository

The repository's default branch keeps the earlier prototype's name. Next to
T17 it still holds:
- the PKCE browser-handoff sign-in, which R14 replaces;
- the Git smart-HTTP and Artifacts providers, which R15 replaces;
- the old Sync API and its database.

Removing it, or marking it historical, is a decision for the maintainer before
M4 adds the data API.

## What holds

**Contract conformance:**
- All four endpoints keep the contract's paths, fields, media types, and error
  codes.
- `client_id` is checked before the plugin runs.
- The public token endpoint stays form-encoded. Better Auth 1.7.28 accepts
  only JSON there, so the service converts form to JSON internally.
- Device endpoint requests with an unknown or repeated field get
  `invalid_request`.
- Every response carries `Cache-Control: no-store`.
- Codes last 600 s, and the poll interval is 5 s.

**Device description:**
- The name is trimmed and counted in code points, at most 64; the platform
  must be `macos`.
- Both are stored as two extra columns on the plugin's own row, filled in for
  this request only. There is no second table and no patch to the plugin.
- Consuming or deleting the code removes them with it.

**Approval page:**
- The page is rendered on the server and runs no browser JavaScript.
- Every value is HTML-escaped. The CSP is `default-src 'none'`, and forms
  post only to the page itself or to GitHub.
- Every POST must carry the service's exact `Origin`. An `Authorization`
  header is refused on browser actions, and cookies are dropped whenever a
  bearer token is present.

**Secrets and logs:**
- Better Auth logging is off, and adapter errors become a plain
  `server_error`.
- Invocation logs and traces are off in the deployed config.
- The console OTP sender exists only in the dev entry. A development-mode
  build fails on purpose, and the staging bundle contains neither the sender
  nor the dev entry.

**Isolation:**
- Each environment has its own D1 database. Rate limits are stored in D1,
  keyed by `cf-connecting-ip`.
- No KV, Durable Objects, or Queues.

**Scope:** 15 files, +1,900 / −47 lines, within the estimate. No deploy.
