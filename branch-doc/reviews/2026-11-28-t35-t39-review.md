## T35–T38 notes

- **R-1, medium, T37: offline sign-in shows a browser error page.**
  - When the service cannot be reached before sign-in, the system window opens
    and shows Safari's own connection error.
  - The person must close it. The App then returns to signed out with no
    message.
  - The "Couldn't reach SkillDeck Cloud" state is reached only when the code
    exchange fails, which is rare. The card's airplane-mode case was meant to
    show it.
  - Fix: before opening the window, make one quick request to the origin. On
    a connection failure, show "failed: network" and open no window.
- **R-2, medium, T35: the service sign-in page is English and light only.**
  - A person using the App in Chinese signs in on an English page.
  - Fix:
    - the App sends a `ui_locales` value (`en` or `zh`) with the sign-in
      request;
    - the page shows its text in that language, falling back to
      `Accept-Language`;
    - the page follows the system light or dark appearance.

    This changes the contract. It needs exact page text in both languages.
- **R-3, low, T36: every unexpected failure maps to `protocol`.**
  `signInWithBrowser` catches every exception and returns
  `CloudSignInFailed(protocol)`, including a failure to write the session
  store. This is safe, because nothing leaks and the App shows "Sign-in didn't
  finish". But it hides real defects. Acceptable for now; revisit if field
  reports show that message often.
- **R-4, low, T38: source IDs depend on the installation seed.**
  - `sourceIdFor` uses `cloud/source-id-seed` under the App support
    directory.
  - The ID is stable across rename, restart, publish, and name change, as the
    card asked.
  - It is not stable if the seed file is lost while the Workspace survives.
    Every Device-Bound Skill would then look replaced.
  - Confirm that the seed and the Workspace live and die together. If they do
    not, record it as a known limit.
- **Good: staging acceptance found a real defect.** A signed-in top-level GET
  with no `Origin` or `Referer` returned 500. Codex reproduced it, fixed it
  narrowly, added a regression test, and redeployed. Replay revocation,
  wrong-verifier rejection, and the end of the browser session were checked
  live.

## T39: what the screenshots show

- **Codex's flags are mechanical.** It counted, for example, "two secondary
  buttons" and "the text says KiB".
- **A look at the screenshots finds problems that matter more,** in this
  order:
  1. **Dead ends:**
     - "同步因错误停止。" / "Sync stopped after an error." and the storage-limit
       notice sit in the sidebar with no cause and no action;
     - the person cannot tell what happened or what to do.
  2. **Choices without consequences:**
     - Attention states offer two equal buttons, for example "接受来源替换" /
       "仅保留在这台设备".
     - Neither says what happens to this Mac's unsynced changes, and none is
       recommended.
     - This is the riskiest pattern, because a wrong click can discard work.
  3. **The note conflict dialog:**
     - the same thing has two names ("云端备注" and "传入的笔记");
     - "保存处理结果" is not natural Chinese;
     - at the default window size the editor is cut off, so the person cannot
       see what they will save.
  4. **The new-Device sheet:**
     - agent rows show a filesystem path;
     - the checkbox touches the agent icon;
     - Skills have no description;
     - with three Skills the sheet already scrolls.
  5. **Technical words:**
     - "slot" in English;
     - KiB and Unicode units in limit messages.

     File names such as `SKILL.md` in the change review are fine: the people
     reviewing a diff are Skill authors.
- **Rework cards must fix exact states and text,** as T37 did, ordered as
  above. Item 2 needs the maintainer to confirm what each choice does to
  unsynced local changes before text can be written.
