## Items

### 1. The generic operation layer branches on one operation kind

Severity: medium.

**Where:**
- `lib/src/application/operations/operation_coordinator.dart:234`: skips
  revision reference reconciliation after sealing the plan;
- `operation_coordinator.dart:376` and `:408`: delete the journal straight
  after a rollback;
- `lib/src/infrastructure/database/drift_operation_control_plane.dart:902`:
  writes no Operation Record unless the operation succeeded.

All four compare `record.kind` with `WorkspaceOperationKind.applyRemoteState`.

**Why it matters:**
- Before this change the coordinator and control plane knew no operation kind.
  Every later kind with the same needs (T08 install, T09 Removal) would add
  more branches.
- The Decision Log does not mention the branches, so review checklist item 3
  is not met.
- The control-plane branch hides real failures too. A cancelled apply, or one
  that fails on a corrupt pack, now leaves no Operation Record either.
- No test asserts that a `noChange` or `draftResolutionRequired` apply leaves
  no Operation Record, so the reason for the branches is not pinned down.

**What the branches are for:** `noChange` and `draftResolutionRequired` are
returned by throwing out of `prepareCandidate`, which rolls the envelope back.
Without the branches each of those answers would add a failed record to the
person's operation history. Separately, remote objects only reach the live
Store in the applying phase, so reference reconciliation before that would see
missing objects.

**Fix (T11):** express these needs without naming the kind in generic code,
and record failures again. The card leaves the mechanism to Codex.

### 2. Repeat semantics and the order of the Draft check

Severity: low. Card and contract defect.

- T07's acceptance said a repeated successful call returns `noChange`. The
  contract's retry rule says a repeat either finds the state applied or fails
  the guard. Codex followed the contract: a repeat with the old
  `expectedEffective` returns `staleSnapshot`, and a repeat with the refreshed
  guard returns `noChange`. That is accepted. The card now says so.
- Contract rule 1 put the Draft check first. With a Dirty Draft and L = R, the
  call returns `draftResolutionRequired`, which would show the Attention Reason
  "Incoming change waits behind a Draft" when nothing is incoming. The contract
  now checks L = R and "R is an ancestor of L" first. The code follows in T11.

### 3. No cheap read of the current Effective and Upstream

Severity: low. Contract gap, open.

The only public way to learn a Skill's current Effective `RevisionId` is
`exportRevisionPack`. After a `staleSnapshot`, `skills_cloud` must either
export a pack or rely on a value it cached from an earlier result. That works,
because a changed Effective also appears in the committed-change feed and
usually needs an Upload anyway, but it is wasteful. Decide when writing T08
and T09, or in M4: add the RevisionIds to the feed entry, add a small read, or
keep caching.

**Decided 2026-11-24:** option C. The maintainer chose a small read operation,
`inspectRevisionSelections`. See the contract's "Seam 4: current revisions"
and `../tasks/T12-inspect-revision-selections.md`.

### 4. A full Store copy on every apply

Severity: low.

`prepareRemoteRevisionStore` in `lib/src/composition/remote_revision_store.dart`
copies the whole live Store before it knows the outcome, so a call that ends
in `noChange` still pays for the copy. Phase 1 Skills are small, so this is
acceptable. T11 may decide L = R before the copy. Measure the rest in M8.

### 5. Sync candidates are recognized by parent count

Severity: nit.

`readMergeParent` returns the second parent of any two-parent commit, and the
Update candidate paths now call it for every candidate. That is safe today
because `RevisionCommitRequest` limits Update candidates to one parent. If that
ever changes, the native function should check the Sync candidate commit kind
as well.

### 6. T06's Progress and Outcome

Severity: nit. T06's last Progress item ("Run the full acceptance gates after
integration") is unchecked, and its Outcome lists only targeted suites. The
full-suite result is in T07's Outcome. Tick it in T11.

### 7. T10

The private ADR-0105 is outside this repository, so this review cannot check
it. The proposal's status line and the README were updated as the card asked.
Codex reports a byte comparison against the proposal.

### T08-1: Store recovery fails after two local publishes

**Found by:** a probe Codex ran for this review on macOS, using local Sources
only:
1. install a Skill, then publish two Drafts;
2. close the Workspace and move its Store aside;
3. reopen it.

**Result:**
- Reopening fails with `recoveryFailed`, `{reason:
  revisionReferenceReconciliationFailed}`.
- The rebuilt Store holds the install commit and the second publish, but not
  the first. SQLite still lists three Published Revisions.
- While the Workspace is closed, history, export, and Restore Publish all
  throw `StateError`.

**Cause:**
- Every operation rebuilds the Recovery Bundle from a few current roots. For
  example, publish keeps `[commit]` plus the current Upstream and Effective
  (`revision_preparation_service.dart`).
- The native recovery pack adds each root's commit and tree, not its parents.
- So earlier Published Revisions that SQLite and the retention refs still list
  are missing from the bundle.

**Scope:**
- The same root selection is in `main`, from the initial snapshot, so the
  defect is very likely older than Cloud. It has not been reproduced on `main`.
- It also limits T08: the donor history in the initial bundle lasts only until
  the next operation on that Skill.
- For sync, a Device that loses a Store cannot open its Workspace, so it
  cannot export either.

**Options for the maintainer:**
- (a) Retain every Published Revision that SQLite lists as a bundle root.
- (b) Always build the bundle with history.
- (c) Narrow what reconciliation expects after recovery, and accept truncated
  history.

(a) keeps the existing native call and the manifest's meaning, so it is the
likely smallest fix. The maintainer chose (a) on 2026-11-25:
`../tasks/T13-recovery-bundle-roots.md`, ahead of T09.

### T13-1: remote-only ancestors after a Store loss

**Codex's probe:**
- A Skill was fast-forwarded by `applyRemoteState` over a remote-only
  intermediate commit.
- After the loss, open succeeded and the Skill reported `recovered`.
- The intermediate object was missing, and export failed with
  `revisionStoreCorrupt` with no file written.

**Cause and impact:**
- This is the expected limit of option (a): the bundle keeps only objects that
  this Device's SQLite lists.
- For Personal Sync, that Skill can no longer be exported, so it stops
  syncing until the maintainer picks a remedy.
- T08's initial install bundle carries the donor's history, but only until the

**Decision, 2026-11-25:** every Recovery Bundle carries the full history of
its roots. If the live Store lacks part of that history, the bundle falls back
to roots-only, so a Store rebuilt from a short bundle before the fix keeps
working. Such a Store still cannot export; repairing it needs the revisions
from the Cloud again, which is M7's concern. Card: `../tasks/T14-recovery-bundle-history.md`.
